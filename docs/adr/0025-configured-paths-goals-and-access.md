# Configured paths, goals and access

A shared QualificationPath is a unique combination of specialization, qualification kind and scope. A separate user–path assignment holds the exam access scope (written, oral or both) and archive state. A user may have at most five assignments in total, including archived ones. `maxUserQualificationPaths` in domain preparation configuration owns this limit. The onboarding command checks capacity under the same account lock as insertion; retries for an existing assignment and restoration remain allowed at the limit. The selected assignment belongs to each client, independently of other devices; the backend persists no selection. Scope can only widen, from written or oral to both. Changing the selection or passing the exam date never removes history or revokes access.

Onboarding loads dependent options from the catalog and requires a target session matching the specialization's parent chamber. A district chamber is optional, and study never requires one. A session has an explicit availability window that includes oral preparation after the written exam. Onboarding has no personal oral-date input and submits `oralExamDate: null`; planning uses the session's labelled approximate oral date. The versioned goal API retains its optional personal oral date for a separate future editor. The final command creates the assignment and first goal atomically, validating the configuration again. The successful client saves its selection locally. Retrying neither duplicates the assignment nor overwrites an existing goal.

UserExamGoal is versioned. Changing the session or date appends a new version without repointing earlier activity; commands use the goal version as their expected version. Web keeps committed onboarding choices in the URL. Each step owns a small form initialized from its committed value; editing remains local until the user confirms that step. Confirming a parent selection clears its dependent choices, including when that selection is unchanged; navigating backwards alone preserves the committed draft. Public and authenticated onboarding compose the same step forms explicitly through their own route APIs. Earlier steps never grant access.

Paths are a section of the account profile: add, select, archive and restore. Access extension is offered through its dedicated screen. The profile displays goal details but has no goal editor; the backend retains versioned goal changes for a separate UI. Archiving removes no history and never changes another client’s selection. On each client, an unavailable or archived selection falls back to the first non-archived assignment in the ordered list and immediately persists that fallback; if none remain, it clears the local selection. Opening a study kind outside the user's scope offers an explicit extension to both, currently free, and then returns to the originally requested page. Opening the page alone never extends anything.

Daily planning, XP, rankings and reset execution are separate work (ADR-0010).

## Public onboarding

Onboarding is public until the configuration is saved. Separate endpoints return specializations, dependent kinds and scopes, and exam sessions, in public contract groups without authentication. Individual assignments and mutations stay protected and their data appears only after sign-in. The final public step renders a session query boundary: loading disables its submit button, a session permits starting, and absence offers sign-in. Submission validates and commits the final selection before redirecting. The redirect keeps the full draft and an onboarding intent in the URL, so sign-in explains why authentication is needed. The completion mutation persists configuration and selects the returned active path locally; its caller owns user-facing toast messages.

## Client-local selection and assignment pagination

The web stores the selected shared QualificationPathId in an account-scoped cookie readable during SSR. Mobile uses its own local storage when implemented; no server endpoint synchronizes selections. Web resolves its saved ID against a complete ordinary-query response requested with the assignment limit. The five-assignment cap makes pagination unnecessary for this client flow. A missing, malformed, foreign or archived ID falls back to the first active assignment and is written immediately. The onboarded beforeLoad resolves and synchronizes selection. Components read route context; explicit selection changes save the cookie and invalidate the router. Profile remains accessible without an assignment, and highlights its list using the saved ID from the authenticated context. Selection alone sends no backend mutation.

Client-readable web cookies use the shared host-only `Secure`, `SameSite=Strict`, `Path=/` policy. A cross-site entry may omit the saved cookie on its initial request, so authenticated routes defer their guards to the browser for cross-site or unclassified requests. Ordinary same-site and direct requests retain SSR. Selection synchronization still runs in the onboarded beforeLoad, after the browser can read its saved choice; an external entry never overwrites that choice based on an incomplete request cookie header.

GET /preparation/paths keeps its cursor pagination contract. Web navigation, onboarding guards and profile use the same ordinary-query cache entry with the configured maximum as page size. A separately named infinite-query factory remains available with an independent cache key. It includes archived assignments and orders by the assignment’s trigger-maintained `updated_at` descending, then path ID ascending to break ties. The cursor contains that timestamp and path ID, independent of whether the cursor's assignment remains available. The timestamp changes on assignment insertion and updates through its existing database trigger. Material reads, goal-history inserts and client-local selection do not touch the assignment or record activity. There is no separate activity timestamp or activity-writing API behavior. As with other mutable sorted collections, a concurrent assignment update can move an assignment ahead of an already issued cursor; a fresh traversal sees the current order.

The initial preparation migration is edited in place for the independent V2 pilot; local development data is recreated. No selection table, selection HTTP operations or last-selected timestamp remain.

Catalogue specializations have stable codes and a nullable description, which distinguishes railway structures from railway traffic control without expanding their display names. Kinds and scopes also expose stable codes. Scope pages return restricted before unrestricted, with that order included in the cursor. Exam-session pages sort chronologically with an ID tie-breaker. The onboarding session step requests only the two nearest available sessions. Published dates carry `isConfirmed`; clients prefix estimated written dates with `~`, including the selected goal. Development seed dates cite their chamber sources and explicitly flag estimates.
