# Schema ownership and module layers

Every data schema has exactly one home, decided by what it describes. A single value or rule that clients and the backend both need is **vocabulary** and lives in `@inzpro/domain`: branded identifiers, literal codes, value primitives such as `UtcIsoDateTime`, `QuestionCount` and `PageLimit`, limits and pure helpers like `nextUserExamGoalVersion`. Any object that crosses HTTP is a **DTO** and lives in `@inzpro/api-contracts`: resources, requests, responses, pagination parameters and envelopes, and transport errors. Everything else is private to the owning API module: **models** with `DateTimeUtc` and `Option`, business errors, ports, and **rows** that stay inside their PostgreSQL adapter. `@inzpro/domain` therefore contains no object schemas, and the backend's cursor mechanics live in `apps/api/src/lib`.

A module model is declared independently of its DTO and of its rows, even when they share most fields. A model built by spreading DTO fields made the backend domain depend on the public HTTP shape, and rows derived from models chained a single API change through three layers. The duplicated fields are the price of letting the API, the domain and the database change separately. Rows decode straight into the model only when the columns match it one to one; otherwise the adapter declares a private row schema and maps it explicitly.

Each API module is split into layer folders: `domain/` (models, rules, business errors), `application/` (commands, queries, policies, reader and repository ports, infrastructure errors), `infrastructure/` (PostgreSQL adapters) and `http/` (`handlers.ts` per contract group, `mappers.ts` for DTOs and `errors.ts` for contract errors). Only folders with content exist. Dependencies point inward: `http → application → domain`, and infrastructure implements application ports. Only `http/` imports `@inzpro/api-contracts`. Its `mappers.ts` converts in both directions with plain functions, so handlers never re-decode an already validated payload into a model. A model without rich values may be returned as its DTO directly, and the handler's response type checks it. Other modules permitted by `apiModuleDependencies` in the architecture policy, which keeps module dependencies acyclic, may use a module's `domain/` and `application/`, plus another module's `http/mappers.ts` and `http/errors.ts` from `http/`. Its `infrastructure/` is wired only by `http/handlers.ts` and by the worker's composition in `src/worker/`, the second entry point of the same backend (ADR-0012). This replaces ADR-0012's "layers only where they have a real role": with fixed folders, the `conventions/module-layers` lint rule can check placement and dependency direction, and `conventions/domain-vocabulary` keeps object schemas out of `@inzpro/domain`.

## Considered options

- **Shared object schemas in `@inzpro/domain`**: this was the earlier layout. In practice the package collected DTOs with ISO strings, and backend models then extended them.
- **Effect `Model.Class` with select, insert and JSON variants from one definition**: rejected because it couples the contract package to persistence variants and hides the DTO/model/row split we want reviewers to see.
- **Flat module folders with role suffixes only**: rejected because the direction of dependencies cannot be checked by path, and ten roles in one folder stopped being readable.
